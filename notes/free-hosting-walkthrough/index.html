Notes / Walkthrough

From laptop to live, in an afternoon.

This is the step-by-step version of the free hosting recipe — the actual moves, not just the pitch. You’ll create two free accounts yourself, then hand the rest to your AI tool.

What you need first

Two accounts, both free, both take about a minute. This is the one part nobody can do for you — an AI tool can’t sign a Terms of Service on your behalf.

GitHub

Where your code lives and gets its version history. Sign up with an email or your Google account, whatever’s fastest.

Vercel

What actually puts your site on the internet. Sign in with “Continue with GitHub” instead of a new email and password. It links the two accounts in one step and saves you doing it later.

A domain (optional)

If you want yourname.com instead of a project.vercel.app address, buy it now from any registrar. Not required to get started — this is easy to add later, in step 04.

Point your AI tool at them

This is the part that turns your AI tool from something that talks about code into something that can actually push it. MCP (Model Context Protocol) lets it talk to GitHub and Vercel directly, creating repositories, pushing commits, triggering deploys, without you relaying every command by hand.

Ask your AI tool something like
Connect yourself to my GitHub and Vercel accounts using MCP, so you can create repositories, push code, and deploy on my behalf.
Or, if you’re driving Claude Code directly
claude mcp add --transport http vercel https://mcp.vercel.com claude mcp add --transport http github https://api.githubcopilot.com/mcp/

Either command opens a one-time sign-in in your browser. Approve it, and you’re connected.

If a connection won’t authorize (it happens, MCP is still young), you haven’t lost anything. Any capable AI tool already knows how to drive the gh and vercel command-line tools directly, the same way a developer would type them. Just make sure it’s running them through npx vercel rather than a global install. A stale local copy can hang onto a login token that’s already expired, and it’ll fail with a confusing error instead of just reauthenticating.

Worth knowing

DNS changes are the one thing to make by hand.

Everything above is safe to let an AI tool drive on its own. Pointing a live domain somewhere new is the exception, since a mistake there can take a real site offline. Have it tell you exactly what to change, then make the change yourself.

Get it online

From here it’s the same three moves every time: your files go into a GitHub repository, that repository gets connected to a Vercel project, and Vercel publishes it. Once that connection exists, every future change goes live automatically the moment it’s pushed.

Ask your AI tool something like
Create a GitHub repository for this project, push everything to it, connect it to a new Vercel project, deploy it, and give me the live URL when it’s done.
Or, the manual version
gh repo create my-site --private --source=. --push npx vercel link npx vercel --prod

Vercel reads what kind of project it is and configures the build itself. There’s nothing to set. You’ll land on a free address ending in .vercel.app — live there for a while before you touch a domain. It’s the exact same site either way, and there’s no rush.

Add your own domain

The shape of this step is the same everywhere, even though every registrar’s dashboard looks different: you add the domain in Vercel, Vercel tells you exactly one DNS record to add, and you go add that record wherever you bought the domain. Then you delete anything left over from wherever the domain used to point.

Ask your AI tool something like
I want to point my own domain at this Vercel project. Tell me exactly which DNS record to add, and check whether anything old needs to be removed first.
Or, to add the domain yourself
npx vercel domains add yourdomain.com npx vercel domains inspect yourdomain.com
  • Whatever’s already pointed at your old host has to go first — DNS won’t let two different records answer for the same name.
  • If you want yourname.com and www.yourname.com to both work, that redirect is a setting inside Vercel’s dashboard, not something you add in DNS.
What tripped me up

Old records block new ones

Anything still pointed at your previous host has to be deleted before a new record can take over the same name. If you’ve migrated through more than one host over the years, expect to find more leftover records than you’d guess.

Switch the record type before you paste

In most DNS dashboards, an “A” record field only accepts an IP address. If you’re adding a CNAME instead, change the Type dropdown first. Pasting a hostname into an A field just throws a generic error that doesn’t explain itself.

The www redirect isn’t a DNS setting

Making www.yoursite.com forward to yoursite.com (or the reverse) happens in Vercel’s own dashboard, under the domain’s settings. Looking for it in your DNS records will send you in circles.

Keep new records “DNS only”

If your registrar or DNS host offers a proxy or CDN option (Cloudflare calls it the orange cloud), leave it off for records pointed at Vercel. Vercel needs to see the real traffic directly.

Use npx vercel, not a global install

A vercel command installed once and left alone quietly goes stale, and its saved login can expire without telling you. Running it through npx always pulls something current, and reauthenticating is a non-issue.

Secrets go in the dashboard, never in a chat

If you’re ever asked for an API key or a password during any of this, type it directly into Vercel’s (or GitHub’s) own settings page. Don’t paste it into a terminal command or hand it to an AI tool in conversation. Nothing here actually requires that.

That’s the whole thing, start to finish. If any of this still feels abstract, the short version, and the reasoning behind it, is back on the overview.
